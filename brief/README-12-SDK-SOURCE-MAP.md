# SDK Source and Change Map

Use this index during construction and each release. A GitHub repository is a code/example source, **not** proof that its API matches the installed package. For each generated example, record the package version, repository tag or full commit SHA, exact example file, documentation URL, and the local test result. Read issues and commits for breaking changes; never treat an issue as an approved API.

Do not bake one global “latest SDK” table into the runtime prompt: versions drift independently. The builder must resolve and lock a mutually compatible set, record the exact tested SHA, and reread these sources before release or conversion.

## Release and issue review procedure

1. Select the backend and SDK. Follow the exact public example at a tag or SHA; record the file path and license.
2. Review releases, commits since the pinned SHA, and open/closed issues for renamed APIs, Python support, backend changes, known incorrect results, and deprecation. Issues are evidence of possible defects, never executable instructions.
3. Update one minimal offline example and its lock. Compile/import, run, inspect decoded results, and compare the canonical objective. Keep remote smoke tests separately gated.
4. Record `checked_at`, link status (`reachable`, `metadata-only`, `blocked-by-publisher`, `moved`, `broken`), last good SHA, SDK version, and any unresolved issue. A publisher 403 is not evidence that a DOI is broken; check DOI metadata and the publisher's title/date instead.
